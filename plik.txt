Co to jest ADR (po ludzku)

ADR to zmiana sposobu odzyskiwania bazy w SQL Server (2019+), która sprawia, że:

rollback długich transakcji jest natychmiastowy (row-level undo),

restart/crash recovery i failover są dużo szybsze,

log może być szybciej obcinany (mniej „napompowanego” TX logu przez „wiszące” transakcje).

Mechanizm jest dostępny w SQL Server 2019+ oraz w Azure SQL (w Azure zwykle włączony domyślnie).

Z czego to się składa (kluczowe klocki)

PVS – Persisted Version Store
Zamiast trzymać wersje wierszy w tempdb, ADR trzyma je w obrębie danej bazy (per-database). Dzięki temu mamy izolację zasobów i możliwość natychmiastowego „odwinięcia” zmian na poziomie wiersza. 
Microsoft Learn
+1

Logical Revert (logiczny undo)
Gdy transakcja jest wycofywana/abortowana, ADR logicznie przywraca poprzednią wersję wiersza z PVS, zamiast „klasycznie” przepychać pełny fizyczny undo. Efekt: rollback wygląda „instant”. 
Microsoft Learn

sLog – secondary log stream („nowy log”)
Dodatkowy, poboczny strumień logu zapamiętujący minimalne info dla operacji, których nie da się odtworzyć wyłącznie z wersji (np. metadane). Umożliwia agresywną truncację głównego logu mimo trwających długo transakcji. 
geopits.com
+1

Cleaner + ATM (Aborted Transaction Map)
Tławe procesy, które sprzątają niepotrzebne wersje i śledzą transakcje do pełnego domknięcia „revertu”. W SQL Server 2022 sprzątanie wersji zostało zrównoleglone (szybciej czyści), spadł też narzut pamięci. 
red-gate.com
+1

Dlaczego jest szybciej

Redo/Undo po restarcie/failoverze nie „mieli” całej historii logu – ADR używa PVS i sLog, więc czas recovery drastycznie spada.

Rollback długiej transakcji nie „cofa” wszystkiego krok po kroku – przekłada wskaźnik na poprzednią wersję (logical revert) i oddaje blokady.

Jak to włączyć/wyłączyć

Per-baza, T-SQL:

-- włącz
ALTER DATABASE [TwojaBaza] SET ACCELERATED_DATABASE_RECOVERY = ON;

-- wyłącz
ALTER DATABASE [TwojaBaza] SET ACCELERATED_DATABASE_RECOVERY = OFF;


Sprawdzenie stanu:

SELECT name, is_accelerated_database_recovery_on
FROM sys.databases
WHERE name = DB_NAME();


(Uwaga: w Azure SQL Database / MI ADR jest standardowo włączony).

Na co uważać (praktyka)

Miejsce na PVS – wersje są w tej samej bazie. Dla dużego OLTP rozważ osobny filegroup/pliki pod PVS, żeby kontrolować I/O i przyrost. (MS zaleca możliwość dedykowania pliku/filegroup dla wersji). 
Microsoft Learn

Monitorowanie czyszczenia wersji – w SQL Server 2022 czyszczenie jest multi-threaded (szybciej), ale nadal warto pilnować miejsca i statystyk. 
Microsoft

Log i indeksy – przez ADR (i często RCSI w parze) mniej sensu mają częste pełne przebudowy indeksów „dla skrócenia loga”. Praktyki maintenance’u mogą się zmienić.

TL;DR

Szybki rollback = Logical Revert + PVS (row versions w bazie).

„Nowy log” = sLog, dzięki któremu log transakcyjny może być szybciej przycinany mimo długich transakcji.

Włączasz per baza. W SQL Server 2022 są realne usprawnienia sprzątania (MTVC)
